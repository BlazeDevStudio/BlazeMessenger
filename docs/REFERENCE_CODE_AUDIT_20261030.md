# LAN Messenger — Comparative Source & Release Audit
**Audit date:** 2026-10-30 (Asia/Manila)  
**Repository:** BlazeDevStudio/BlazeMessenger, apps/LAN-Messenger  
**Frozen source HEAD:** a49ff04e48fc971ff59f5f62d1888baac04c802b (owner draft PR #17; no merge)  
**Scope:** Dart networking/cryptography, UI and state, file transfer, WebRTC and groups, Windows native call/toast, Android Activity/permissions/PiP/ringtones, generated icons, build/tests/signing. This is a source and CI review, **not** a penetration test or a completed physical device acceptance test.

## Executive verdict

**RELEASE / SECURITY NO-GO**. Source builds on Windows and Android but unpaired discovery peers are admitted, file reception is enabled by default, long-term static X25519 keys and local plaintext storage lack ratchet / at-rest protection, and full cross-device CI is RED. The prior owner's Windows error at 192.168.1.188:58159 proves a refused advertised TCP endpoint at that instant; it does not alone establish the exact OS/root cause. Explicit call and remote-control consent safeguards already exist and must remain.

**Executed CI evidence:** [exact-head six-job run 41005030604](https://github.com/BlazeDevStudio/BlazeMessenger/actions/runs/41005030604): Windows build+smoke **PASS**, Android release build/test/signing **PASS**; android-install, android-pair-lan, android-pair-video/PiP and android-peer-process-death **FAIL**. Android logs show intermittent ADB disconnection/emulator errors and app-process exits, so blame attribution needs per-process tombstones and actual call traces. [Docker run 41005030612](https://github.com/BlazeDevStudio/BlazeMessenger/actions/runs/41005030612): **7/7** encrypted localhost TCP/discovery regressions pass. Neither proves physical Windows-to-Android video calling. Build assets remain *preview only*.

### Cross-project architecture references (documentation only)

1. **LocalSend published protocol** — https://github.com/localsend/protocol/blob/main/README.md : multicast discovery, registration, prepare-upload/accept, per-file token and checksum responses. Apply acceptance and quota concepts; LAN Messenger's native encrypted framing is different.
2. **KDE Connect protocol reference** — https://github.com/KDE/kdeconnect-meta/blob/work/protocol-schemas/protocol.md : identity, explicit pairing, capability negotiation and rejection of unpaired device operations.
3. **Jami call lifecycle** — https://docs.jami.net/developer/jami-concepts/calls.html : candidate exchange, ICE negotiation, TLS/DTLS transport separation and device call states.
4. **WebRTC peer connections** — https://webrtc.org/getting-started/peer-connections : SDP signaling, trickle ICE, actual connected-state detection.
5. **Signal X3DH and Double Ratchet specifications** — https://signal.org/docs/specifications/x3dh/ and https://signal.org/docs/specifications/doubleratchet/ : identity authentication, replay discussion, forward secrecy and per-message key evolution. LAN Messenger **does not implement Signal protocol**.
6. **Android PiP developer guidance** — https://developer.android.com/develop/ui/views/picture-in-picture : correct video surface, visibility transitions, auto-enter and OS ownership.
7. **Android notification channels and sound URIs** — https://developer.android.com/develop/ui/compose/notifications/channels and https://developer.android.com/reference/android/app/NotificationChannel : channel immutability and stable sound URI warning.
8. **OWASP file upload cheat sheet** — https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html : quotas, naming, content trust, storage and decompression/preview attack surface.

No third-party app source, brand assets or non-permissively licensed code are copied into this audit or proposed changes. This is a comparison of public documentation; every implementation will need a dedicated license and provenance check.

## Acceptance plan, in priority order

- **P0 Gate A — Trust:** Unknown newly seen self-keyed device must never be able to silently write a file or control local device; owner can view discovered peer, verify its fingerprint and pair/revoke deliberately. Test pairing revocation, key rotation conflict, relaunch and corrupted key backup.
- **P0 Gate B — Calls:** Repeat 30 physical Windows→Android and Android→Windows voice/video calls each, foreground/minimized/game/background, with opt-in audio/video; collect two-sided WebRTC traces and WER/Android tombstones; all terminations release native resources, no fatal exceptions.
- **P0 Gate C — Six-job:** At exact head all Windows build+smoke, Android build+sign, install/launch, 2-device LAN Answer, video/PiP and killed-peer tests must execute and pass. Emulator failures require a separate classification, not suppressed gates.
- **P1 Gate D — File stress:** Unknown peer refuse, explicit approved large transfer, disk-full, rename collision, power-off/restart at chunk/commit boundary, same-filename concurrent files and replayed completion; verify no overwrite/duplicate and bounded disk.
- **P1 Gate E — Field UX:** Test Android 12–16 notification actions, configured sound and accessibility/notification permissions on OEM hardware; Wi-Fi isolation, Windows Firewall port policy, multi-NIC/VLAN routing, Bluetooth helmet headsets, screen off.
- **P1 Gate F — Protocol fuzz:** 1,000 malformed UDP announcements, slow HTTP clients, forged key changes, stale/replayed signaling and out-of-order peer messages, independently fuzzed JSON/frame boundary checks.
